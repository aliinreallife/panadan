| Owned data | Optional separate PostgreSQL 18 platform with ingest schema, restricted runtime roles, raw revisions, normalized facts and transactional cursors; not the source reporting DB. |
| Operations | Docker/Compose for VPN/web/platform, private ingress overlays, systemd templates, guarded CLI/controller, backup/restore tools, GitHub Actions. |

Observed code flow (not a deployment diagram):

```text
Browser session -> FastAPI/Jinja dashboard
REST bearer ----> FastAPI reporting routes -----> fixed reporting queries -> source PostgreSQL (READ ONLY)
MCP bearer/JWT -> transport gate -> per-tool policy -> same reporting queries
All current identity/grant checks -> auth Store (SQLite default)
Approved operator sync -> source reader -> ingest_batch -> owned PG raw revisions/jobs/checkpoints
                                             -> deterministic normalize:v1 -> derived facts
External host telemetry publisher (separate) -> JSON reader -> admin health card
```

The repository has one main web service, not a fleet of independently deployed microservices. The owned ingest database is not the active reporting read path in the inspected code. Do not replace the working reporting route simply because the target knowledge architecture differs.

## 5. Specific technical risks observed during Phase 1

These are audit findings or review hypotheses, not a prioritized Phase 2 gap analysis.

- **Isolation:** global account/source namespaces and ID-only lookups; adding customers before server-side row/tenant isolation would be unsafe. Worker scope and source restrictions must also be evaluated, not just UI visibility.
- **Permission semantics:** field-level response projection is real but some queries fetch broader fixed columns. `permissions()` falls back to role defaults on malformed override JSON, whereas field policy fails closed. Legacy NULL grants/token snapshots can preserve broader defaults; assess migrations and negative cases before reuse as general policy.
- **Transcript contract mismatch:** historical README/STATUS describe raw browser transcript and sensitive details; audited `project_call()` excludes raw transcription even for detail responses. The explicit browser/MCP excerpt routes redact and audit separately. Reconcile intended browser UX and test contract without broadening disclosure. Masking is not anonymization; names, context and other sensitive content can remain.
- **Sync correctness:** source edit-marker coverage, stable unique IDs, deletions, replay ordering across streams, retention and load need verification. Checkpoints prevent stale stream advancement but do not by themselves prove event freshness across different streams. A tombstone is not physical erasure.
- **Processing reliability:** transactional queue rollback is useful, but retries, poison-job handling and visibility need review before expensive/long-running model work. Current implementation is a deterministic in-transaction processor, not an AI pipeline runner.
- **Source vs destination:** never widen the reporting account or reuse it for outbound writes. Separate owned PG privileges and a separate future destination integration must retain this distinction.
- **OAuth and auth migration:** issuer/client identity and production IdP flow require independent acceptance; staged PG auth is intentionally not production-selectable; do not run simultaneous auth authorities or silently enable both token modes.
- **Audit/operations:** historical deployment documentation and current source can drift; generic activity audit failure is swallowed, and private production overlays are not wholly source-controlled. Backup freshness, restoration, retention, dependency/edge hardening and alerts require runtime evidence.
- **Public repository:** no private customer identity, source payload, commercial strategy, credentials or actual production configuration included here. Future discovery and approved private evidence must remain outside public history.

## 6. Recommended review and remaining evidence

Reuse the existing FastAPI/Jinja shell, read-only reporting adapters, identity/session infrastructure, current access policy primitives, owned PostgreSQL, transactional ingestion and operations/test tooling within their verified boundaries. Extend these incrementally. Do not start by replacing the frontend, introducing a second auth authority, rebuilding the sync system or adding speculative services.

Before treating the audit as production-complete, obtain sanitized read-only operator evidence for the active image and commit, effective deployment topology, source grants and source-ID/update/delete contract, owned PG schema/roles and aggregate sync health, current auth/OAuth mode and client smoke results, backup/restore freshness and real UI/access behavior. No real data disclosure or production change is required to obtain metadata-level evidence. A fresh isolated local verification using the documented locked test commands remains recommended when a checkout and dependencies are available.

Review this inventory with the product owner first. Phase 2 will compare the accepted decisions against these findings only after explicit review/approval. No priority assignment, design/migration choice, source changes, application implementation, deployment or customer use-case selection is made here.
